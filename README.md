# DataMapperApp

An ASP.NET Core Web API that stores a single SQL Server table through the [Data Mapper](https://martinfowler.com/eaaCatalog/dataMapper.html) pattern. `EntityController` depends on `IDataMapper`. Configuration chooses the implementation at startup, so the same HTTP API can run on ADO.NET, Dapper, or EF Core.

| Mapper | What you write | Where the SQL lives |
|---|---|---|
| `AdoNetDataMapper` | Connection, parameters, and a column-by-column read of `SqlDataReader` | `SqlCommandHelper`, shared with Dapper |
| `DapperDataMapper` | Connection and parameters | Same commands; Dapper maps each row onto `Entity` |
| `EfCoreDataMapper` | Changes to an `Entity` tracked by `EntityDbContext` | Generated by EF Core from the `Entity` model |

ADO.NET and Dapper call the same parameterized commands. EF Core does not use `SqlCommandHelper`. That split is the comparison: the first two make the SQL visible, and EF Core hides it behind the model.

## Requirements

- [.NET 10 SDK](https://dotnet.microsoft.com/download)
- Docker, for the SQL Server container below, or your own SQL Server

## Run the database

From the repository root:

```bash
docker compose up -d
```

Compose starts SQL Server on `127.0.0.1:14333` and applies `database/create-entity.sql`. The container password is a local development password, `Dev_Only_Password1`. The script creates a database named `Development` and this table:

```sql
CREATE TABLE dbo.Entity
(
    Id      int           IDENTITY(1,1) NOT NULL CONSTRAINT PK_Entity PRIMARY KEY,
    Name    nvarchar(200) NOT NULL,
    Created datetime2     NOT NULL,
    Updated datetime2     NOT NULL
);
```

`docker compose up` is safe to repeat. The script creates the database and table only when they are missing.

To run the script yourself against another server:

```bash
sqlcmd -C -S localhost,14333 -U sa -P Dev_Only_Password1 -v DatabaseName=Development -i database/create-entity.sql
```

## Configure the connection

`AppSettings:DataConnectionString` in `appsettings.json` is empty on purpose. The API refuses to start until a connection string is set. User secrets and environment variables both override that file.

For the Compose database, from the repository root:

```bash
dotnet user-secrets set "AppSettings:DataConnectionString" "Server=localhost,14333;Database=Development;User Id=sa;Password=Dev_Only_Password1;TrustServerCertificate=True" --project DataMapperApp
```

Or, for the current shell:

```powershell
$env:AppSettings__DataConnectionString = "Server=localhost,14333;Database=Development;User Id=sa;Password=Dev_Only_Password1;TrustServerCertificate=True"
```

`AppSettings:DataMapperClassName` selects the mapper. The default is `AdoNetDataMapper`. The other values are `DapperDataMapper` and `EfCoreDataMapper`. An unknown name stops startup and lists the three names. The process logs the active mapper as it starts.

## Run the API

```bash
dotnet run --project DataMapperApp
```

The `https` launch profile listens on `https://localhost:7205` and `http://localhost:5224`, and opens Swagger at `/swagger`.

## API

Base route: `/Entity`. Create and update take `name` as a query parameter. Update and delete take `id` as a query parameter.

| Method | Route | Success | Missing id | Blank or too-long name |
|---|---|---|---|---|
| `GET` | `/Entity` | `200` and a JSON array ordered by `Id` | | |
| `GET` | `/Entity/{id}` | `200` and one entity | `404` | |
| `POST` | `/Entity?name=Ada` | `201`, a `Location` header, and the new entity including its identity | | `400` |
| `PUT` | `/Entity?id=1&name=Ada` | `200` and the updated entity | `404` | `400` |
| `DELETE` | `/Entity?id=1` | `204` | `404` | |

`Name` is required and limited to 200 characters. `Created` and `Updated` are set to UTC on insert. Update changes `Updated` and leaves `Created` as it was.

```http
POST /Entity?name=Ada
GET /Entity/1
PUT /Entity?id=1&name=Ada+Lovelace
DELETE /Entity?id=1
```

## Tests

```bash
dotnet test
```

`DataMapperContractTests` is one suite, inherited by the ADO.NET, Dapper, and EF Core test classes, so each mapper has to satisfy the same behavior. When Docker is running, those tests start their own SQL Server container. Otherwise, on Windows, they use LocalDB and a database named `DataMapperAppTests`. Controller status codes and mapper registration are covered without a database.

## Layout

```
database/create-entity.sql                         Database and Entity table
docker-compose.yml                                 SQL Server on port 14333, then the script
DataMapperApp/
  Program.cs                                       Host, Swagger, startup log
  Controllers/EntityController.cs                  HTTP CRUD over IDataMapper
  Data/EntityDbContext.cs                          EF Core model for Entity
  DataMappers/
    IDataMapper.cs                                 Async create, read, update, delete
    DataMapperServiceCollectionExtensions.cs       Reads AppSettings and registers one mapper
    AdoNetDataMapper.cs                            SqlClient and manual mapping
    DapperDataMapper.cs                            Same SQL, Dapper mapping
    EfCoreDataMapper.cs                            DbContext, no hand-written SQL
  Helpers/SqlCommandHelper.cs                      Parameterized SQL for ADO.NET and Dapper
DataMapperApp.Tests/                               Shared mapper contract, controller, and registration
```

## Add another mapper

1. Implement `IDataMapper`. Use `DataMapper` as the base when the new type only needs the connection string.
2. Register it in `AddDataMapper` and add its name to `DataMapperNames`.
3. Subclass `DataMapperContractTests` and construct the new mapper there. The existing facts then run against it.
4. Set `AppSettings:DataMapperClassName` to that name.
